mTLS-Handshake: Zertifikat mit speziellen DN-Merkmalen

stellt automatisch ein kurzlebiges Token aus (10 min)

  • Heute besitzt jeder Client einen Keystore mit privatem Schlüssel – manuell enrollt, wiederkehrend erneuert
  • Gestohlener Keystore = Zugriff bis zum Ablauf oder bis das Zertifikat gesperrt ist
  • Ziel: Die Workload besitzt nichts Dauerhaftes – die Plattform bestätigt ihre Identität per kurzlebigem Token
Unser heutiger Weg: mutual TLS mit speziell gestalteten Client-Zertifikaten. Der Server liest Merkmale im Subject-DN und mappt sie auf Rollen bzw. Spring-Security-Authorities. Das Problem ist nicht die Prüfung auf Serverseite, sondern dass jeder Client einen privaten Schlüssel besitzen, enrollen und pflegen muss. Workload Identity dreht das um: Die Plattform, auf der die Software läuft, bestätigt deren Identität.
