Was im Token steht – und was geprüft wird

Header

alg: RS256

kid: <Key-ID>

Geprüft

  • nur RS256 oder ES256
  • kid wählt den Schlüssel aus dem JWKS

Payload

iss: https://issuer-web

aud: wif-demo-validator

sub: system:serviceaccount:wif-demo:consumer

exp / iat / nbf: Laufzeit 600 s

kubernetes.io: Namespace, Pod, SA

Geprüft

  • iss exakt gleich dem erwarteten Issuer
  • aud enthält exakt wif-demo-validator
  • exp und nbf, 60 s Toleranz für Uhrabweichung
  • sub, iat und exp müssen vorhanden sein

Signatur

RS256 über Header und Payload, erzeugt mit dem privaten Schlüssel des Clusters

Geprüft

  • gegen den öffentlichen Schlüssel aus dem JWKS verifiziert
  • Alles erfüllt → HTTP 200 mit den Claims; eine einzige Abweichung → HTTP 401 mit kurzem Grund
  • Prüfung mit Nimbus JOSE + JWT, rein lokal – kein Netzwerkaufruf pro Anfrage
Das Token ist ein ganz normales JWT. Neu für viele ist nur die audience-Bindung: Das Token ist ausschließlich für den Validator ausgestellt und wird von jedem anderen Dienst abgelehnt.
