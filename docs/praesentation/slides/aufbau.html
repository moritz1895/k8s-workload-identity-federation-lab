Anhang: Startreihenfolge mit docker compose up

1

pki-init, sa-keys

  • Lab-CA und Serverzertifikate, auch für den Ingress
  • Signaturschlüssel des Clusters

2

server (k3s)

  • Kubernetes-Cluster in einem Container
  • Token-Issuer https://issuer.wif.local

3

bootstrap

  • legt Namespaces, ServiceAccounts und Pods an, darunter den Discovery-Pod
  • Ingress-Zertifikat, Traefik-Einstellungen, Härtung von wif-issuer-discovery

4

ingress-lb

  • einziger Weg der Prüfer in den Cluster, nur TCP 443
  • bereit, sobald der Discovery-Pod das JWKS über den Ingress ausliefert

5

Dienste

  • keycloak + gateway
  • service-r (Dienst R)
  • validator (Variante)
  • Auf dem Host nur Docker + Compose v2 – alles andere läuft in Containern, in drei getrennten Netzen
  • Reihenfolge über Compose-Abhängigkeiten: Ein Dienst startet erst, wenn seine Vorgänger bereit bzw. erfolgreich beendet sind
  • Keycloak startet erst, wenn das JWKS über ingress-lb abrufbar ist; die Cluster-Schlüssel lädt es bei Bedarf und cacht sie
Ein docker compose up baut das komplette Lab. pki-init und sa-keys laufen einmal und beenden sich, ebenso bootstrap. Danach gleicht der Discovery-Pod im Cluster Discovery-Dokument und JWKS alle 15 Sekunden mit dem API-Server ab, auch bei einem Schlüsselwechsel. k3s bringt Traefik als Ingress-Controller mit; bootstrap passt ihn an und spielt die Admission-Regeln ein, bis dahin gibt es im Lab nur den Admin. service-r braucht beim Start nur sein Zertifikat; die Discovery bei Keycloak macht es erst beim ersten Token.
