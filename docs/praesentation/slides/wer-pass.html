Was ist die Identität?Merkmale im Subject-DNNamespace + ServiceAccount (sub)
Wer bekommt sie?wer bei der RA ein Zertifikat für diesen DN genehmigt bekommtwer im Namespace deployen oder Tokens anfordern darf
Wer kann mitlesen?Root auf dem Server mit dem Keystorewer in den Pod darf (exec), Cluster-Admin, der Node des Pods

  • Genehmigen muss der Eigentümer der Identität: Deploy-Rechte im Namespace stehen in Git, jede Änderung braucht das Review des Fachbereichs, dem der Namespace gehört
  • Ein einziger Weg für Änderungen (GitOps); Admin-Rechte nur befristet und mit einer zweiten Person
  • Audit-Log des Clusters außerhalb des Clusters: Alarm bei Token-Anforderungen, exec und neuen Rechten im Namespace
Der private Schlüssel lag auch heute nie ganz exklusiv bei der Anwendung: Root auf dem Server hatte ihn, und die RA konnte jederzeit ein zweites Zertifikat mit demselben DN genehmigen. Neu ist nur, wo diese Stellen sitzen. Die gefährlichste Lücke ist der Prozess: Beantragt Fachbereich C Deploy-Rechte im Namespace von A, darf nicht der Vorgesetzte von C genehmigen, sondern nur A. Sonst laufen Cs Pods mit As Identität, ohne dass A es merkt. Ein Antrag bei Keycloak nützt C dagegen nichts: Ein Client, der an As sub gebunden ist, hilft nur, wer einen Pass mit As sub vorlegen kann. Vorsicht bei wiederverwendeten Namen: sub enthält nur Namespace und ServiceAccount, keine ID. Legt C einen gelöschten Namespace von A mit gleichem Namen neu an, bekommt C As Identität. Deshalb Namensräume pro Fachbereich (Präfix, per Admission-Regel erzwungen) und Namen nicht wiedervergeben.
